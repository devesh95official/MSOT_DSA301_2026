Why this matters more than it looks

Almost every tree operation costs O(height), not O(N): searching a BST, inserting, walking one root-to-leaf path, and the memory used by recursion. Two trees with the same number of nodes can therefore differ by a factor of N / log N in cost. That is the entire reason AVL trees, red-black trees, std::map and database indexes exist.
Where the log comes from. A perfect tree of height h holds 2h+1 − 1 nodes, because level d holds 2d of them. Turn that round: N nodes need only about log₂N levels. A skewed tree wastes that completely — each level holds one node, so h = N − 1 and the tree is a linked list with extra pointers.
The practical failure. A skewed tree of 100,000 nodes means 100,000 nested calls. Typical stack limits are a few tens of thousands of frames, so a perfectly correct recursive traversal segfaults. This is the only real reason to convert a traversal to the iterative form (pages 6–8) or to Morris (page 13).
What does not change. Visiting every node is O(N) on both shapes — a full traversal cannot be beaten by balancing. Balance helps the operations that follow one path, not the ones that must see everything.

How a skewed tree happens

Insert 1, 2, 3, 4, 5 into an empty BST in sorted order. Every value is larger than everything already there, so every insert goes right, and you have built a chain. Sorted input is the worst case for a plain BST — which is exactly why self-balancing trees rotate after inserts.
The balanced tree on the left is built the other way round: take the sorted array, make the middle element the root, and recurse on the two halves. That is LeetCode 108, and it is three lines:
TreeNode* build(vector<int>& a, int lo, int hi) {    if (lo > hi) return NULL;    int mid = (lo + hi) / 2;    TreeNode* r = new TreeNode(a[mid]);    r->left  = build(a, lo, mid - 1);    r->right = build(a, mid + 1, hi);    return r;}
