The master template — every tree recursion is this

ReturnType solve(TreeNode* r) {    if (r == NULL) return answerForEmptyTree;   // BASE CASE    ReturnType L = solve(r->left);              // ask the left    ReturnType R = solve(r->right);             // ask the right    return combine(L, R, r->val);               // one line of yours}
Only two things ever change between problems: what the base case returns, and the combine line. Everything else you have already written. Switch jobs above and watch how little of the code moves.

The base case is always the identity of whatever you are combining with: 0 for +, INT_MIN for max, true for &&. Pick the value that cannot change the answer, and the empty tree takes care of itself.

Two directions of information

Goes down — arguments

Comes up — return value

This is the question to ask about any new tree problem: does a node need something from above, or from below? “Depth”, “path sum so far”, “largest value seen on the way here” travel down as extra parameters. “Height”, “count”, “is my subtree balanced”, “best path inside me” travel up as return values. Some problems need both, and then the return type becomes a small struct.
Try the depth job, then the height job, on the same tree. Depth is known immediately on the way in; height cannot be known until the way out. That single contrast explains why some tree problems feel easy and others feel impossible.

If you are stuck on a tree problem, answer these four

      
1What should the function return for an arbitrary node? Say it in one sentence before writing any code.
2What is the answer for an empty tree? That is your base case.
3Given the left answer and the right answer, how do you combine them?
4Does anything need to be passed down? If so it is an extra parameter, not a return value.
If you cannot answer question 1 in one sentence, you are not ready to write the code — and no amount of staring at the tree will help. Write the sentence first.
